# REQUIREMENTS 분석 및 설계 결정

## 1. 문서 목적
- `PROBLEM.md`의 명시 요구사항을 구현 가능한 수준으로 구체화한다.
- 명시되지 않은 항목은 합리적 가정으로 결정하고 근거를 남긴다.
- 구현 우선순위(동작 여부 -> 핵심 기능 -> 사고의 깊이)에 맞춰 현재 상태를 추적한다.

## 2. 범위
- 포함:
  - 백엔드 REST API
  - 초기 데이터 동적 생성
  - 동시성 제어
  - API 문서(OpenAPI + Markdown)
  - 테스트 자동화
  - 운영/보안/관측성 기본기
- 제외:
  - 프론트엔드 UI
  - 인증/인가
  - 고급 학사 정책(선수과목, 학년 제한 등)

## 3. 명시 요구사항 정리

### 3.1 필수 API 기능
- 학생 목록 조회
- 교수 목록 조회
- 강좌 목록 조회(전체/학과별), 정원/현재 인원/시간 포함
- 수강신청
- 수강취소
- 내 시간표(이번 학기) 조회
- 헬스체크: `GET /health` -> `200 OK`

### 3.2 핵심 비즈니스 규칙
- 정원 초과 금지
- 학생당 최대 신청 학점 `18`
- 동일 시간대 중복 수강 금지
- 동시 요청 상황에서도 정원 일관성 보장
  - 예: 잔여 1석 강좌에 다수 동시 요청 시 1명만 성공

### 3.3 데이터 구축 요구
- 서버 시작 시 초기 데이터 생성 완료
- `GET /health`가 `200`이면 즉시 API 사용 가능
- 시작 후 1분 내 데이터 생성 + 서버 준비 완료
- 최소 규모
  - 학과 10+
  - 교수 100+
  - 강좌 500+
  - 학생 10,000+
- 정적 대량 데이터 파일(SQL/CSV) 사용 금지
- 현실적인 데이터 패턴 사용

## 4. 모호한 요구사항에 대한 결정

### 4.1 인증/인가
- 본 과제 범위에서 인증/인가는 도입하지 않는다.
- 대신 수강신청/취소/시간표 조회는 `student_id`를 명시 입력받는다.

### 4.2 학기 범위
- 데이터 및 API는 "이번 학기" 단일 컨텍스트(`2026-1`)로 운영한다.

### 4.3 시간 충돌 판정
- 충돌 판정식: `a_start < b_end and b_start < a_end`
- 동일 요일 + 1분이라도 겹치면 충돌로 간주한다.

### 4.4 학점 정책
- 강좌 학점 범위: `1~3`
- 총 신청 학점이 18을 초과하면 신청 실패(`409 CREDIT_LIMIT_EXCEEDED`)

### 4.5 중복 신청/취소 정책
- 동일 강좌 중복 신청: `409 ALREADY_ENROLLED`
- 미신청 강좌 취소: `404 ENROLLMENT_NOT_FOUND`

### 4.6 목록 조회 정책
- 커서 기반 페이지네이션 사용: `limit`, `cursor`
- 응답 형태: `items`, `next_cursor`
- 정렬 기본값: ID 오름차순

## 5. 동시성 제어 전략

### 5.1 목표
- 정원 초과 방지 및 학점/시간 충돌/중복 신청 규칙을 동시성 환경에서 일관되게 보장

### 5.2 전략
- MySQL(InnoDB) 트랜잭션 사용
- 수강신청/취소 시 `students`, `courses` 대상 `SELECT ... FOR UPDATE` 적용
- 검증 + 상태 변경을 단일 트랜잭션으로 수행

### 5.3 검증 기준
- 잔여 1석 동시 요청에서 성공 1건, 실패 N-1건
- 최종 `enrolled <= capacity` 항상 참

## 6. 데이터 생성 설계

### 6.1 생성 원칙
- 실행 시 동적 생성(코드 로직 기반)
- 이름/학과/강좌명 토큰은 코드 상수로 보유, 레코드는 런타임 조합 생성
- 스키마는 SQL 파일(`infra/mysql/init/01_schema.sql`)로 관리
- 대량 데이터는 startup 코드(`src/app/services/seed_service.py`)에서 생성

### 6.2 생성 규칙
- 학과: 12개
- 교수: 120명
- 강좌: 600개
- 학생: 10,000명
- 강좌 시간표: 요일/시간 슬롯 조합으로 생성

### 6.3 정합성 보장
- 외래키/체크/유니크 제약 활용
- `enrolled` 초기값 정합성 유지
- 고아 참조(없는 학생/강좌/교수 참조) 금지

## 7. API/에러 응답 표준

### 7.1 성공 응답
- 2xx + 리소스 데이터

### 7.2 에러 응답 형식
```json
{
  "code": "COURSE_FULL",
  "message": "강좌 정원이 가득 찼습니다.",
  "details": {
    "request_id": "..."
  }
}
```

### 7.3 주요 에러 코드
- `INVALID_REQUEST` (400)
- `STUDENT_NOT_FOUND` (404)
- `COURSE_NOT_FOUND` (404)
- `ENROLLMENT_NOT_FOUND` (404)
- `ALREADY_ENROLLED` (409)
- `COURSE_FULL` (409)
- `CREDIT_LIMIT_EXCEEDED` (409)
- `SCHEDULE_CONFLICT` (409)
- `INTERNAL_SERVER_ERROR` (500)

## 8. 운영/보안/관측성 요구(추가 평가 대응)

### 8.1 운영 안정성
- 앱 시작 훅은 FastAPI lifespan 사용
- startup 초기화는 락 기반으로 중복 실행 방지

### 8.2 관측 가능성
- 모든 응답에 `X-Request-Id`, `X-Process-Time-Ms` 헤더 제공
- 구조화 요청 로그 기록(request id, method, path, status, duration, client ip)
- `LOG_LEVEL`로 로그 레벨 제어

### 8.3 보안 기본기
- 기본 설정에서 내부 예외 원문 비노출
- `APP_DEBUG=true`일 때만 내부 예외 메시지 노출
- 에러 응답 details에 `request_id` 포함
- CORS는 `CORS_ALLOW_ORIGINS` 환경변수 기반 allowlist

## 11. 불명확한 부분에 대한 판단과 결정 사항(상세)

### 11.1 헬스체크의 의미
- 판단 기준:
  - 평가자는 `GET /health` 성공 시 즉시 API 사용 가능 상태를 기대한다.
- 최종 결정:
  - `health`는 단순 프로세스 생존 여부가 아니라, DB 연결 가능 + seed 완료 상태를 반영한다.
  - startup/lifespan에서 seed가 끝난 뒤 `completed=true` 상태를 노출한다.
- 미선택 대안:
  - 앱 프로세스만 살아 있으면 `200`을 주는 방식은 제외했다.
  - 이유: 실제 사용 가능 상태와 괴리되어 평가 환경에서 오해를 유발할 수 있다.

### 11.2 seed 실행 정책(부분 데이터 존재 시)
- 판단 기준:
  - 최소 개수 미달 상태의 부분 데이터는 테스트 결과를 불안정하게 만든다.
- 최종 결정:
  - 핵심 테이블 중 하나라도 최소 개수 미달이면 seed를 다시 수행한다.
  - 재생성 시 참조 무결성 보장을 위해 연관 테이블 정리 후 재삽입한다.
- 미선택 대안:
  - 부족한 테이블만 증분 채우는 방식은 제외했다.
  - 이유: 데이터 분포의 불균형 및 중복 규칙 검증 결과 왜곡 가능성이 커진다.

### 11.3 시간 충돌 규칙의 경계 처리
- 판단 기준:
  - "1분이라도 겹치면 충돌"이라는 요구를 수학적으로 일관되게 표현해야 한다.
- 최종 결정:
  - 충돌 판정식 `a_start < b_end and b_start < a_end`를 사용한다.
  - 예: `10:00-11:00`과 `11:00-12:00`은 비충돌, `10:00-11:00`과 `10:59-12:00`은 충돌.
- 미선택 대안:
  - 시작/종료 경계 포함 비교(`<=`)는 제외했다.
  - 이유: 연속 강의(끝나는 시각과 시작 시각이 같은 경우)까지 충돌로 처리되는 부작용이 있다.

### 11.4 에러 상태코드 정책
- 판단 기준:
  - 클라이언트가 재시도/수정 가능성을 구분할 수 있어야 한다.
- 최종 결정:
  - 리소스 부재: `404`
  - 비즈니스 규칙 위반(정원/중복/학점/시간충돌): `409`
  - 요청 유효성 실패: `400`
- 미선택 대안:
  - 모든 실패를 `400`으로 단순화하는 방식은 제외했다.
  - 이유: 에러 의미가 뭉개져 테스트 작성성과 운영 분석성이 떨어진다.

### 11.5 페이지네이션 선택
- 판단 기준:
  - 대용량 조회에서 지연 증가와 중복/누락 가능성을 줄여야 한다.
- 최종 결정:
  - `offset` 기반 대신 `cursor` 기반(`id > cursor`)으로 통일한다.
- 미선택 대안:
  - `offset` 기반은 구현 단순성은 높지만, 데이터 증가 시 비용이 커지고 동시 변경 구간에서 안정성이 낮다.

### 11.6 테스트 DB 접속 재현성
- 판단 기준:
  - 로컬과 CI에서 동일한 방법으로 테스트를 반복 실행할 수 있어야 한다.
- 최종 결정:
  - 테스트 시작 시 `.env` 또는 `.env.example`을 로딩하고 DB 기본 환경값을 주입한다.
- 미선택 대안:
  - 실행자 수동 환경변수 설정 의존 방식은 제외했다.
  - 이유: 사람/환경마다 설정 누락으로 실패가 발생해 재현성이 낮다.

## 12. 설계 의사결정 및 근거(상세)

### 12.1 계층형 아키텍처 채택
- 결정:
  - `api -> services -> repository -> database` 분리, DTO/응답 모델은 `domain`에 배치.
- 근거:
  - 책임 경계를 명확히 해 변경 영향 범위를 줄인다.
  - 테스트 시 비즈니스 로직을 API 계층과 독립적으로 검증할 수 있다.

### 12.2 SQLAlchemy + Repository 패턴
- 결정:
  - ORM(SQLAlchemy)와 Repository를 사용해 쿼리 책임을 별도 모듈로 분리.
- 근거:
  - 쿼리 로직이 서비스 로직에 섞이지 않아 가독성과 유지보수성이 높다.
  - 추후 인덱스/쿼리 튜닝 포인트를 한 곳에서 관리하기 쉽다.

### 12.3 동시성 제어 위치
- 결정:
  - 애플리케이션 락이 아닌 DB 트랜잭션 + 행 잠금(`FOR UPDATE`)으로 제어.
- 근거:
  - 멀티 인스턴스 환경에서도 동일한 정합성 모델을 유지할 수 있다.
  - "잔여 1석" 같은 경쟁 조건을 DB 수준에서 일관되게 해결 가능하다.

### 12.4 검증 로직 순서
- 결정:
  - 수강신청 시 존재 확인 -> 중복 확인 -> 학점 확인 -> 시간 충돌 확인 -> 정원 확인 -> 등록 순으로 처리.
- 근거:
  - 실패 사유를 명확하게 반환할 수 있다.
  - 불필요한 후속 연산을 줄여 트랜잭션 시간을 단축한다.

### 12.5 관측성 기본기 포함
- 결정:
  - 요청 단위 추적 헤더(`X-Request-Id`, `X-Process-Time-Ms`)와 구조화 접근 로그를 기본 포함.
- 근거:
  - 평가 및 운영 관점에서 문제 재현/원인 추적 속도를 높인다.
  - 테스트에서도 추적 헤더의 존재를 검증 가능하다.

### 12.6 에러 응답 하드닝
- 결정:
  - 기본 설정에서 내부 예외 원문 비노출, 디버그 모드(`APP_DEBUG=true`)에서만 노출.
- 근거:
  - 불필요한 내부 정보 노출을 줄여 보안 기본기를 충족한다.
  - 개발 환경에서는 디버깅 효율을 유지한다.

### 12.7 문서 이중화(OpenAPI + Markdown)
- 결정:
  - 기계가 읽기 쉬운 OpenAPI와 사람이 빠르게 확인 가능한 Markdown을 함께 유지.
- 근거:
  - 평가자가 문서만으로 테스트 케이스를 작성하기 쉬워진다.
  - 변경 시 계약 문서와 설명 문서를 동시에 검토할 수 있다.

### 12.8 커밋 분할 원칙
- 결정:
  - 기능/리팩터링/문서/테스트를 가능한 분리된 커밋으로 유지.
- 근거:
  - 변경 의도와 영향 범위를 추적하기 쉽다.
  - 회귀 발생 시 원인 커밋을 빠르게 식별할 수 있다.
