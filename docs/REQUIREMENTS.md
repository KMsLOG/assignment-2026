# REQUIREMENTS 분석 및 설계 결정

## 1. 문서 목적
- `PROBLEM.md`의 명시 요구사항을 구현 가능한 형태로 구체화한다.
- 명시되지 않은 항목은 합리적 가정으로 결정하고 근거를 남긴다.
- 구현 우선순위를 따라 MVP(동작/핵심 기능/견고성) 기준을 확정한다.

## 2. 범위
- 포함: 백엔드 REST API, 초기 데이터 생성, 동시성 제어, API 문서화.
- 제외: 프론트엔드 UI, 인증/인가 고도화, 학사정책 고급 규칙(선수과목/학년제한 등).

## 3. 명시 요구사항 정리

### 3.1 필수 API 기능
- 학생 목록 조회
- 교수 목록 조회
- 강좌 목록 조회(전체/학과별), 정원/현재인원/시간 포함
- 수강신청
- 수강취소
- 내 시간표(이번 학기) 조회
- 헬스체크: `GET /health` -> `200 OK`

### 3.2 핵심 비즈니스 규칙
- 정원 초과 금지
- 학생당 최대 신청 학점 `18`
- 동일 시간대 중복 수강 금지
- 동시 요청 상황에서도 정원 일관성 보장
  - 예: 잔여 1석에 100명 동시 신청 시 1명만 성공

### 3.3 데이터 구축 요구
- 서버 시작 시 초기 데이터 생성 완료
- `GET /health`가 `200`일 때 즉시 API 사용 가능 상태
- 시작 후 1분 내 데이터 생성 + 서버 준비 완료
- 최소 규모
  - 학과 10+
  - 강좌 500+
  - 학생 10,000+
  - 교수 100+
- 정적 대량 데이터 파일(SQL/CSV) 사용 금지
- 의미 있는 현실적 데이터 패턴 사용

## 4. 모호한 요구사항에 대한 결정

### 4.1 인증/인가
- 이번 과제에서는 인증/인가를 도입하지 않는다.
- 이유: 평가 핵심은 동시성/비즈니스 규칙이며, 테스트 단순성을 우선한다.
- 대신 수강신청/취소/시간표 API는 `student_id`를 명시 입력받는다.

### 4.2 학기 범위
- 데이터 및 API는 "이번 학기" 단일 컨텍스트로 운영한다.
- 이유: 문제에서 시간표 조회 범위를 "이번 학기"로 명시.

### 4.3 시간표 표현과 충돌 규칙
- 시간표 필드 형식: `"월 09:00-10:30"` 문자열.
- 충돌 판정: 요일이 같고 시간 구간이 1분이라도 겹치면 충돌로 간주.
- 기준 시간대: 로컬 고정(UTC 변환 없음), 분 단위 비교.

### 4.4 학점 정책
- 강좌 학점 범위: `1~3`학점(현실성 + 구현 단순성).
- 학생 총 신청학점 > 18이면 신청 실패.

### 4.5 중복 신청/취소 정책
- 이미 신청한 동일 강좌를 다시 신청하면 실패(`409 Conflict`).
- 신청하지 않은 강좌를 취소하면 실패(`404 Not Found` 또는 `409`; 본 구현은 `404` 채택).

### 4.6 목록 조회 정책
- 대용량 데이터를 고려해 기본 페이지네이션 제공(`limit`, `offset`).
- 정렬 기본값은 ID 오름차순.

## 5. 동시성 제어 전략 (핵심)

### 5.1 목표
- 정원 초과 방지와 학생별 규칙(학점/시간충돌/중복신청)을 동시성 환경에서도 일관되게 보장.

### 5.2 전략
- MySQL(InnoDB) 트랜잭션 + 행 잠금을 사용한다.
- 수강신청 시 `students`와 `courses` 행을 `SELECT ... FOR UPDATE`로 잠근다.
- 동일 학생 요청은 학생 행 잠금으로 직렬화하고, 동일 강좌 요청은 강좌 행 잠금으로 정원 초과를 방지한다.
- 수강신청/취소 API는 단일 트랜잭션으로 검증 + 상태변경을 함께 수행한다.

### 5.3 성공/실패 기준
- 잔여 1석 강좌에 동시 요청 100개:
  - 성공 1, 실패 99
  - 최종 `enrolled <= capacity` 항상 참

### 5.4 대안 및 선택 이유
- 애플리케이션 레벨 락 대신 DB 일관성 메커니즘을 우선 사용해 다중 인스턴스 확장 시에도 동일한 정합성 모델을 유지한다.

## 6. 데이터 생성 설계

### 6.1 생성 원칙
- 실행 시 동적 생성(코드 로직 기반).
- 소규모 토큰(성/이름 조합, 학과명, 강의명 어근)은 코드 내 상수로 보유.
- 완성 레코드는 런타임 조합으로 생성.
- 스키마(SQL)는 정적 파일로 관리하되, 대량 데이터는 앱 startup 코드(`src/app/seed_data.py`)에서 생성한다.

### 6.2 생성 규칙
- 학과: 10~12개 고정 목록.
- 교수: 100명 이상, 학과별 균등 분배.
- 강좌: 500개 이상, 학과/교수/학점/시간표를 조합해 생성.
- 학생: 10,000명 이상, 현실적 한글 이름 패턴으로 생성.
- 시간표는 일정 비율로 충돌 가능한 슬롯을 의도적으로 포함(테스트 가능성 확보).

### 6.3 정합성 보장
- `enrolled` 초기값은 등록 데이터와 일치.
- capacity는 최소 20 이상(예시), enrolled는 capacity 이하.
- 없는 학생/강좌/교수 참조 금지.

## 7. API/에러 응답 표준

### 7.1 공통 응답 원칙
- 성공: 적절한 2xx와 리소스 데이터 반환.
- 실패: 상태코드 + 구조화된 에러 바디 반환.

### 7.2 에러 바디 형식
```json
{
  "code": "COURSE_FULL",
  "message": "정원이 가득 찼습니다.",
  "details": {}
}
```

### 7.3 주요 에러 코드
- `STUDENT_NOT_FOUND` (404)
- `COURSE_NOT_FOUND` (404)
- `ALREADY_ENROLLED` (409)
- `COURSE_FULL` (409)
- `CREDIT_LIMIT_EXCEEDED` (409)
- `SCHEDULE_CONFLICT` (409)
- `ENROLLMENT_NOT_FOUND` (404)
- `INVALID_REQUEST` (400)

## 8. 구현 우선순위 반영 계획
1. 서버 실행 + `GET /health` + 기본 라우팅
2. 초기 데이터 생성(1분 이내, 최소 수량 충족)
3. 목록 조회 API(학생/교수/강좌)
4. 수강신청/취소/시간표 API + 비즈니스 규칙
5. 동시성 제어 적용 및 동시 요청 검증
6. API 문서(OpenAPI 또는 Markdown) 보강

## 9. 테스트 전략
- 단위 테스트
  - 학점 초과 차단
  - 시간 충돌 차단
  - 중복 신청 차단
  - 취소 후 학점/시간표 반영
- 통합 테스트
  - 조회 API 동작/필수 필드 확인
  - 존재하지 않는 ID 처리
- 동시성 테스트
  - 동일 강좌 잔여 1석 동시 신청 시 단 1건만 성공
  - 반복 실행에도 일관된 결과 보장

## 10. 리스크와 대응
- 리스크: startup 시 대량 생성 로직이 느려지면 헬스체크 지연 가능.
- 대응: 배치 insert(`executemany`)와 토큰 조합 생성으로 1분 이내 완료를 목표로 최적화.
