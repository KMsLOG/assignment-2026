### 2) 문제 이해와 핵심 가정
- 본 과제의 1순위는 동작 가능성(빌드/실행/헬스체크), 2순위는 핵심 규칙 정확성(정원/학점/시간 충돌/동시성), 3순위는 사고 깊이(문서/프롬프트/커밋)다.
- 데이터는 정적 레코드 파일이 아니라 런타임 조합 생성이 필수다.
- 동시성 정합성은 애플리케이션 락보다 DB 트랜잭션 + 행 잠금으로 보장하는 것이 다중 인스턴스 확장에 유리하다.
- 목록 조회는 대용량 확장을 고려해 커서 페이지네이션으로 통일한다.

### 3) 주요 의사결정 로그
- 아키텍처: `api -> services -> repository`, DTO/응답 스키마는 `domain`, 전역 예외는 `core`.
- DB/인프라: MySQL 8.4 + Docker Compose, 자격증명은 `.env`로 분리.
- 데이터 생성: startup 시 `seed_service`에서 최소 수량 이상 동적 생성(학과/교수/강좌/학생).
- 동시성 제어: 수강신청/취소를 단일 트랜잭션으로 처리하고 `SELECT ... FOR UPDATE` 적용.
- 문서화: `docs/openapi.yaml`(OpenAPI) + `docs/API.md`(Markdown) 병행 제공.
- 테스트: 카탈로그 조회/검증 오류/비즈니스 규칙/동시성 시나리오를 통합 테스트로 검증.
- 커밋 전략: 기능/문서/리팩터링 단위로 분리하여 변경 의도가 한 번에 파악되도록 유지.

### 4) 품질 점검에서 확인된 리스크와 보완 계획
- 리스크: 프롬프트 파일이 Git 추적되지 않으면 사고 과정 평가 증빙이 누락될 수 있음.
  - 조치: `prompts/codex.md`를 추적 파일로 유지하고, 요청 목록 + 의사결정 근거를 함께 기록.
- 리스크: 요구사항 문서의 seed 코드 경로가 실제 구현과 불일치.
  - 조치: `src/app/services/seed_service.py`로 수정.
- 리스크: 테스트 실행 시 환경변수 미설정이면 DB 접속 실패 가능.
  - 조치: 테스트에서 `.env`/`.env.example`을 로드하고 DB 관련 기본값을 주입.
- 리스크: startup 이벤트 API deprecation 경고.
  - 조치: FastAPI lifespan 방식으로 전환하고, 테스트 호환용 초기화 헬퍼 유지.
- 리스크: 동시성 검증이 서비스 레이어에만 치우칠 수 있음.
  - 조치: API 경유 동시 요청 시나리오 테스트를 추가.

### 5) 이번 턴 반영 항목 요약
- 프롬프트 문서를 “요청 로그 + 사고 근거 + 리스크 대응” 형태로 재정리.

- REQUIREMENTS 문서의 seed 코드 경로 정정.
